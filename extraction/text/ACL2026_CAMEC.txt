A.1 Multi-expert Judge-Guided Evaluation

Algorithm 1 Multi-expert Judge-Guided Evalua-
tion
Input: Question q, Experts E, Initial reports C0 =
   (0)
{Re }, Judge J, Max iterations Tmax = 3, Thresh-
old τ = 8.0, Weights (α, β, γ) = (0.6, 0.2, 0.2)
Output: Final report Rf
t←0
while t ≤ Tmax do
    // Judge evaluates each expert report
    for each e ∈ E do
            (t)       (t)       (t)       (t)
          (se,corr , se,comp , se,safe , δe ) ← J(Ct , pscore )
             (t)       (t)         (t)          (t)
          Se ← αse,corr + βse,comp + γse,safe
    end for
    // Check acceptance condition
               (t)
    if maxe Se ≥ τ then
          // Weighted consensus synthesis
          for each e ∈ E do
                             (t)  P             (t)
               we ← exp(Se ) / e′ ∈E exp(Se′ )
          end for
          Rf ← Synthesize(Ct , {we })
          break
    else if t < Tmax then
          // Dimension-aware revision
          t←t+1
          for each e ∈ E do
                  (t)            (t−1) (t−1)
               Re ← Revise(Re          , δe   )
          end for
                      (t)
          Ct ← {Re : e ∈ E}
    else
          // Max iterations reached, force synthesis
          for each e ∈ E do
                             (t)  P             (t)
               we ← exp(Se ) / e′ ∈E exp(Se′ )
          end for
          Rf ← Synthesize(Ct , {we })
          break
    end if
end while
return Rf

A.2 Case Study
We present three representative cases to demon-
strate CAMEC’s adaptive multi-expert collabora-
tion: (1) iterative refinement when all experts ini-
tially fail to meet quality thresholds (MCS=2.6, Ta-
ble 6), (2) conflict resolution when an expert pro-
duces clinically invalid output (MCS=2.4, Table 7),
and (3) efficient consensus under medium com-
plexity with only two experts activated (MCS=1.6,

uates expert reports across correctness, complete-

back for iterative improvement, and synthesizes
final diagnoses through score-weighted consensus.

inner-product metric). At inference, we retrieve

D.2 Knowledge Graph Construction
We construct a Chinese medical KG from publicly
available medical knowledge sources. After pre-
processing (removing incomplete entries and dedu-
plication), the final KG contains 40,276 entities
(including 8,808 diseases, 5,998 symptoms, 3,828
drugs, and other medical concepts) and 291,503
relations across 11 relation types, stored in Neo4j
v5.18.1.
Subgraph Retrieval. For each query, we per-
form entity linking to identify mentioned medi-
cal terms, then retrieve relevant subgraphs using
predefined Cypher templates. We define 16 tem-
plates covering common clinical intents (symptom
inquiry, treatment recommendation, examination,
etiology, etc.). For example, for a treatment inquiry
about diabetes:
MATCH (d:Disease {name:''})
